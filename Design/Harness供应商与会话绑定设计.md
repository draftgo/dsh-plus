# Harness 供应商与会话绑定设计

状态：部分实施。具体以文末实施进度为准；推荐方案中的其余目标仍待实施。

## 现状与根因

model-picker.jsx 把不认识的供应商组通过 extra 补成工具，导致 RouterGo 混入工具层。tool-profiles.mjs 按工具维护一个 applied 配置，runtime.mjs 的 providerConfig(name) 在启动时读取当前配置，没有会话绑定参数。因此会话重新连接时可能读到另一窗口刚切换的供应商。隐藏 RouterGo 或仅加写文件锁，都解决不了这个问题。

参考版本：reference/cc-switch @ 51ac86f，主要查看 src-tauri/src/services/proxy.rs。

CC Switch 的可借鉴点是工具专用配置适配、工具分区与切换锁。它按应用管理当前目标，与本产品希望同时运行多个不同供应商会话的隔离粒度不同。不能仅凭工具分开配置就推断会话不会漂移。

## 推荐方案

统一供应商数据，按工具做适配，按会话固定路由。三层职责：

1. 供应商库：官方“设置 → 模型”唯一维护入口，保存 URL、凭据引用、模型和适用工具。适用范围只是兼容性/可选范围，不是启用开关；也不代表其所有模型都兼容该工具协议。
2. 工具默认：工具管理只选择“新会话默认供应商”。只影响后续会话，不修改已有会话。
3. 会话绑定：首条消息发送时由服务端创建 routeBinding，含 toolId、providerId、providerRevision、modelId、adapterRevision、bindingRevision、配置快照引用。草稿不创建空会话或启动进程。

供应商只维护一套，工具适配器负责生成工具需要的启动配置，不重复维护密钥。

## 界面与多窗口行为

模型选择同一弹层两级：第一层只列 DSH Harness、Codex、Claude Code、Pi、OpenCode 等执行工具；第二层按供应商分组列出该工具兼容模型。相同模型跨供应商不合并，选择键是 toolId + providerId + modelId。

A 窗口使用 Codex + RouterGo，B 窗口使用 Codex + 其他供应商，二者绑定独立。B 修改工具默认不影响 A，也不影响已经手动选定路由的新聊天草稿。历史会话展示实际绑定，不能展示今天的工具默认。

同一会话被多个窗口打开，仍是同一个服务端会话。切换需要比较 bindingRevision，冲突时刷新；运行中禁止切换。空闲时显式确认并重建驱动；原生工具无法保留历史切换时创建分支并告知，不静默丢失上下文。

工具管理区分“新会话默认”和“同步本机 CLI”。后者才导出到用户全局配置；日常托管会话不靠反复改全局文件启动。

## 真正防漂移需要运行隔离

只记录 providerId 不够。每次托管启动必须从会话绑定生成固定启动配置，使用独立进程及必要的独立配置目录，并明确原生工具的环境、项目配置和全局配置优先级。认证与技能路径单独处理，不可简单改 HOME 导致登录和插件丢失。

- Codex：验证原生每进程配置覆盖、独立 CODEX_HOME 和凭据复用方式，避免托管会话依赖全局 config.toml。
- Claude Code：验证 SDK/CLI 设置优先级，提供会话专用环境和 settings，防止项目配置及继承环境覆盖端点或模型。
- Pi/OpenCode 等：使用其支持的独立配置或进程内供应商定义，逐项验证配置合并规则。
- 工具原生不支持隔离时明确标记“仅全局切换”，不承诺并行隔离。需要补足时再评估本机网关：每个会话独立鉴权与固定路由，绝不复用一个可随时切换的全局目标；不依赖第三方中继。

这些是待验证、待实现的适配目标，不是当前已有能力。

## 更新、凭据和旧会话

URL、协议、模型映射变化生成新修订；已有会话保持固定配置。密钥只在服务端受限存储，绑定保存引用，不放会话 JSON、不发前端、不记日志。官方凭据层若没有版本能力，要明确采用当前引用与轮换规则，不能假称支持历史凭据恢复。

轮换或撤销密钥属于安全动作：不在运行中偷偷更换供应商；按明确策略重新认证或暂停提示。撤销优先于继续运行，失败不能回落到其他供应商。

被引用供应商先停用，再迁移或关闭绑定会话。旧会话缺少绑定时标“来源待确认”，人工确认固定，不能把当前默认当成历史来源。

服务端用 revision/CAS 控制默认和绑定变更；文件锁和校验和仅负责原生配置导出事务。消息执行与路由切换的互斥也必须由服务端保证。

## 验收

1. A/B 同时运行同一工具不同供应商，另一窗口改默认、重启驱动或恢复历史后，路由仍各自固定。
2. 同一会话多窗口操作，旧 revision 不能覆盖新绑定；运行中切换被拒绝。
3. 服务重启后恢复真实来源，供应商不可用则明确报错，不自动改用默认。
4. 输入框显示、实际出站端点和用量统计都使用同一 bindingId 归因。
5. 跨工具委派生成明确子会话绑定，不暗取全局当前配置。

建议实施顺序：分离工具与供应商身份 → 会话绑定/恢复契约 → 逐工具验证运行隔离 → 默认选择、显式切换及 CLI 导出。等待讨论后实施，不只修菜单就宣称完整链路已完成。

## 2026-10-17 配置保护与管理体验

- 新会话默认与本机同步继续分离；原生导出服务内部也强制明确确认、revision 和完整 checksums，不能从内部调用绕过预览。
- 工具管理使用上下布局与品牌图标页签，悬停/键盘焦点展示名称；顶部隐藏横向滚动条，支持按住鼠标左键拖动，编辑区直接展示当前页签内容，不再重复提供侧边工具切换。安装来源、独立副本生命周期、原生配置存在状态明确展示；供应商适用范围沿用品牌资产。
- 经过类型白名单校验的快捷设置纳入会话指纹；模型入口创建会话时捕获当时工具默认快捷设置，后续切换默认不改变已有快照。
- 订阅登录按官方 OAuth 元数据限制到对应工具。Claude/Codex 订阅使用工具本机账户并在连接前核验类型；不复制账户令牌、不把订阅伪装 API 密钥。订阅模式与独立 API 配置/历史隔离模式明确区分。未登录、跨工具或凭据类型不匹配均不静默回退。
- 保留用户原有系统工具入口优先级，DSH+ 更新/重装/卸载仅作用于托管副本。
